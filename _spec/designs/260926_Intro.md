## Response (Claude, 2026-09-26)

I cloned the repo (v0.5.0, 2026-08-26) and read `lib/starter.ex`,
`lib/starter/runner.ex`, and the `starter.new` / `starter.run` tasks. Issue #4

### 1. Do your objections make sense?

Mostly yes. Your reading of the default workflow is correct. `mix starter.new`
writes `lib/mix/tasks/<app>.starter.ex` into the project, and the README says
outright: *"it's the file you'll copy into your next project."* After
`starter.run` finishes, that file is mostly documentation.

There is one correction. The author does offer a reuse mechanism that doesn't
involve copying. It's been there since 0.1.0, before you opened the issue:

- **Step packs.** You put a shared starter module, plus any custom steps, in
  its own small Mix project and pull it in as a dev dep. Then either
  - `mix starter.new --from MyTeam.Starter` copies its steps into the app
    (still a copy, but a generated one), or
  - `{:starter, MyTeam.Baseline}` includes it by reference, and nested
    includes and `if:` flags work too.

So the author's answer to "how do I reuse?" is "make it a package," not
"copy the file." You're right that this is heavier than it should be for one
person with a few app profiles. You'd be maintaining a Mix project just to
hold a list.

A philosophical difference is also worth naming. The author wants **the app to
own its setup** (a reviewable file in the repo). You want **the profile to be
the source of truth** (central config, with git history as the record). Both
positions are reasonable, but upstream may not adopt yours as the default.

### 2. Would it be easy to extract the config to an external resource?

Yes, and easier than it looks, because the step list is already plain data.
The runner only ever calls `starter.steps()` and gets back a list of tuples like
`{:add, :credo}` and `{:remove, :topbar, if: :x}`. Nothing in the engine cares
whether that list came from a hand-written module or from a file. The work
involved:

- **Loading.** You'd read the profile from a file and turn it into that same
  list of tuples.
- **Module coupling.** `Runner.run/3`, `expand_all/2`, and `Starter.flags/1`
  all take a *module* and call `.steps()` on it. They'd need to accept a plain
  list as well, which is a small change. Without touching upstream, you could
  instead build a module at runtime (`Module.create/3`) that returns the loaded
  list.
- **Profile inheritance** (your `use: chat_app`) maps directly onto the existing
  `{:starter, ...}` include. It would just point at a profile name instead of a
  module.
- **Flags.** `info/2` builds the `--flag` schema from `steps()`, so the profile
  has to be known when the options are parsed. That works because `info/2`
  receives `argv`.

Two limits apply to any external config:

1. **Custom steps are code.** A config file can *name*
   `MyApp.Steps.DeployConfig`, but that module still has to be compiled
   somewhere: a step pack dep, or `.exs` files the loader `Code.require_file`s
   from `~/.config/starter/steps/`.
2. **Starter has to be a dep of the target app.** Igniter runs *inside* the
   project, so every new app still needs `{:starter, ..., only: :dev}` in
   `mix.exs`. No config design removes that step, but
   `mix igniter.new my_app --with phx.new --install starter` makes it painless.

### 3. What would be the best approach?

In order of effort:

**A. Zero code: a personal step pack used by reference.** You'd create
`~/src/my_starters` (a tiny Mix project, or even a git repo) containing
`Mix.Tasks.Starters.ChatApp`, `Mix.Tasks.Starters.VoipApp` (which includes
`ChatApp` via `{:starter, ...}`), and your custom steps. In each new app you'd
add it as a `path:` or `git:` dev dep and run `mix starters.chat_app`. No
copying, one source of truth, and custom steps sit next to the profiles. The
only wrinkle is that `mix starter.run` auto-discovery only looks at the app's
own modules, so you call the task by name.

**B. Moderate: an external `.exs` profile file.** I'd recommend this over YAML
if you want the config-file experience. For example,
`~/.config/starter/profiles.exs` would hold a keyword list of
`profile_name => [steps]`, written in exactly the same tuple syntax the README
uses. Compared with YAML:
- It needs no YAML dependency and no translation layer (`if:` and module names
  are already native).
- It's the syntax you'd see in the docs, so examples paste straight in.
- It's loaded with `Code.eval_file/1`, or parsed safely with
  `Code.string_to_quoted/1` if you care about that.

On top of that you'd add the tasks from your issue: `starter.run <PROFILE>`,
`starter.list.profiles`, `starter.list.steps <PROFILE>`, `-c <path>`, plus
`STARTER_CONFIG` env var support. This could be a PR upstream, or a thin
companion package that depends on `starter`, which lets you avoid waiting on
the maintainer.

**C. Full "one command" flow.** You'd wrap B so that
`mix starter.bootstrap my_app chat_app` runs `igniter.new` + `phx.new`, adds
the dep, and runs the profile. It's the nicest UX but has the most moving parts.
I'd only build it after B proves itself.

**My recommendation:** try **A** today, since it costs nothing and tells you
whether a central source of truth is really what you want. If the
Mix-project-for-a-list overhead still bothers you, go with **B** using
`.exs`, and propose it on issue #4 as an *optional* mode alongside the in-app
starter file rather than a replacement. That respects the author's
"app owns its setup" design, which makes it much more likely to be merged.
You could even have `starter.run <PROFILE>` write the resolved step list into
the app as a comment or file, so you keep the documentation benefit too.

Open questions for you:
- Do you need custom step *code* in your profiles, or just built-in steps and
  Hex installers? If it's the latter, B gets simpler.  ANSWER: custom step code
  would be required, but the custom steps would be in standalone
  packages/modules, not in the profiles.
- Upstream PR or your own companion package? ANSWER: separate package (see below)

## My response and next Steps 

First: see my ANSWERS to your open questions above.

Second: I would like to create a new companion package "start_pro" to implement
"starter profiles" that complement the `starter` package.  

The core for start_pro will be taken from the issue I filed (url below) with the
following changes (many suggested by you):  

1) instead of yaml, let's use .exs, with the same list format as used in starter profiles (per your suggestion)
2) each list should be called a 'profile' instead of an app (per your suggestion) 
3) note my issue - an inclusion of a new feature - the "use:" directive which pulls in another profile.  
4) with the 'use' feature, the expanded list of steps must be an acyclic graph - no loops!
5) the mix tasks for 'start_pro' can be as follows (additional/deletions/changes accepted):

```
mix start_pro.config.init           # create a default config file with pre-populated profiles
mix start_pro.config.edit           # bring up the config file in EDITOR
mix start_pro.list.profiles         # lists all profiles 
mix start_pro.list.steps <PROFILE>  # lists all the steps for PROFILE
mix start_pro.run <PROFILE>         # run all the steps for PROFILE
```

all tasks take an optional `-c <config_file_path>` (default: `~/.config/start_pro/profiles.exs`)

Note:
- only one config file is active for any command - multi-config-file support is not required
- issue is at https://github.com/jamilabreu/starter/issues/4
